# Codefront 同步与画面流畅度优化
更新日期：2026-09-13

## 问题、修改与边界
旧实现等待每次请求结束后再休眠 400ms，因此实际快照间隔是网络往返加 400ms。线上三个独立浏览器玩家实测，快照间隔中位数分别约 781、791、862ms；请求往返中位数约 375、386、411ms。浏览器动画帧间隔中位数约 8.3ms，超过 34ms 的帧约 0.08%–0.13%。该设备上的主要问题是状态更新稀疏，不是绘制帧率不足。
同步改为战斗/倒计时阶段以 150ms 为目标周期，并扣除已耗费的请求时间；请求仍串行，不堆积并发。慢请求结束后至少休息 30ms，准备阶段目标周期为 600ms，失败后休息 1 秒，单次请求 5 秒超时。150ms 是理想目标，不是生产网络延迟保证。
画面在相邻快照间，根据已确认动作、速度和目标预测机器人位置，最多预测 350ms。考虑目的地、采集距离、攻击距离、货舱减速、死亡与比赛结束；不预测伤害、采集量或得分，不修改权威 World。收到新快照后平滑校正。失联超过预测窗口后停止推演。
采集波纹、射线和加分文字使用连续展示时钟，不再只随网络快照跳帧。点击机器人使用屏幕展示位置，避免看到的位置和可点击位置偏离。房间栏显示实际请求往返毫秒数，帮助区分网络与画面问题。
核心文件：lib/presentation.ts 定义显示预测和同步节奏；components/Arena.tsx 接入预测与连续特效；app/page.tsx 调度串行请求、超时并展示往返耗时。保留原房间协议、公开访问、Python 执行频率和全部多轮规则。

## 验收与后续维护
16 项规则测试通过，含新增预测不改变权威状态、预测窗口上限、目标/采集范围、死亡/结束冻结及扣除 RTT 的节奏检查。TypeScript 与生产构建通过。
可复用 scripts/performance-check.cjs：三个独立 Chrome 上下文从真实页面创建、加入、验证程序后开战，运行 Python / JavaScript / Python，确认各自实际交付得分，采样同步往返、快照间隔和浏览器帧间隔。PERF_OUTPUT 指定结果文件；TEST_URL 指定网站。测量为单台设备、单次样本，不代表所有地区网络或生产并发容量。
发布前基础浏览器回归检查 Python 执行、热部署、暂停、死循环隔离、手机布局以及多人房间权限。发布后在原公开网站重复性能采样，并记录结果。画面预测是有限的显示补偿，网络慢时仍可能看到小幅校正，不能替代可信服务端实时推送。
本轮不增加新服务或依赖。更高频同步会增加数据库请求量，暂不声称已经做容量压测。如果 RTT 持续很高，应再评估托管平台支持的常驻房间与推送方案；不能只继续压低轮询间隔。
